# Кейс: Тестирование GitLab Tracker (desktop app)

**Продукт:** GitLab Tracker — внутренний десктопный таск-трекер на базе Tauri 2 + React 19 + SQLite. Агрегирует задачи из 87+ GitLab-проектов в одном окне, даёт offline-доступ через локальный кэш и позволяет применять стандарты лейблов на всю группу одной операцией.

**Контекст:** Команда разработки использует GitLab CE как таск-менеджер для 87+ проектов одновременно, хотя GitLab изначально создан для разработки, а не для задач. Трекер решает это: мгновенная загрузка из кэша, drag-and-drop доска, Command Palette (Ctrl+K), аудит соответствия лейблов.

## Ключевые технические риски (из анализа кода)

| Риск | Приоритет |
|---|---|
| Двойной кэш (SQLite + React Query) — два источника истины, расхождение незаметно | 🔴 Высокий |
| Синхронизация: флаг `in_progress` при зависшем синке блокирует все последующие синки | 🔴 Высокий |
| PAT с read-only правами: приложение работает, любой POST/PUT падает с 403 | 🔴 Высокий |
| Drag-and-drop: rollback реализован, но конвергенция React Query и SQLite после сбоя не проверена | 🟠 Средний |
| Экран Соответствия считается по локальному кэшу, не по GitLab — устаревший кэш = ложный «зелёный» | 🟠 Средний |

## Почему Этап 1 (GitLab нативно) — это важно

Трекер — зеркало GitLab. Чтобы тестировать зеркало, нужно знать оригинал.

Перед тестированием трекера я исследовала GitLab нативно: создала тестовый проект-песочницу с полным набором данных (scoped labels, kanban-доска, задачи разных типов, milestone, MR, issue links). Зафиксировала 9 наблюдений — как GitLab ведёт себя на самом деле.

Это даёт точку отсчёта: в Этапе 2 при каждом расхождении можно ответить на вопрос «это баг трекера или так работает GitLab?»
