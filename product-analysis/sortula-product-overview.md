# Sortula — Продуктовый обзор

> Этот документ написан в рамках QA-работы над продуктом Sortula (июль–август 2026).
> Описывает продукт глазами QA-инженера: что это, зачем, кто пользователь, архитектура, критические пути и покрытие тестами.

---

## Что это и зачем существует

Sortula — AI-powered SaaS для сохранения, автоматической классификации и семантического поиска закладок.

**Проблема:** люди сохраняют десятки ссылок в день, но 90% теряется — закладки не структурированы, нет поиска по смыслу, нет резюме. Через неделю пользователь не помнит, что сохранял.

**Решение:**
- Пользователь добавляет ссылку → система извлекает контент автоматически
- LLM генерирует summary, теги, категорию, оценивает "срок жизни" материала
- Семантический поиск по смыслу (не по ключевым словам)
- Доступно из браузера, Telegram, VK и браузерного расширения

---

## Кто пользователь

Люди, потребляющие много контента: статьи, Telegram-каналы, видео, новости — и хотящие к нему вернуться.

**Типичный сценарий:**
> Пользователь читает Telegram-канал, пересылает интересную статью боту Sortula. Через минуту в его ленте появляется закладка с автоматическим summary и тегами. Через месяц он ищет "ML в продакшн" и находит её за секунды.

## Архитектура (вид QA-инженера)

```
Источники входа:
  Web UI (Next.js)          → REST API
  Browser Extension          → Extension Receiver API
  Telegram Bot (aiogram)     → Bot API
  VK Bot                     → VK Webhook

Backend (FastAPI):
  /v1/* endpoints            → Auth → Business Logic → DB

Асинхронная обработка (Celery + Redis):
  URL получена → extract content → LLM analysis → embedding

Хранилище:
  PostgreSQL + pgvector      → данные + векторный поиск
  Redis                      → очереди + кеш
  MinIO (S3)                 → файлы, скриншоты

Внешние сервисы:
  Ollama (LLM)               → анализ контента
  T-Bank / YooKassa          → платежи
```

## Модель данных

Двухуровневая структура закладок:

| CanonicalResource (shared, 1 на URL) | UserBookmark (личная, 1 на пользователя) |
|---|---|
| Извлечённый контент | Личные заметки, теги |
| LLM summary, теги, категория | Статус: прочитано / избранное / архив |
| Векторное embedding | Источник: web / tg / vk / ext |
| Статус LLM-анализа | short_id → /b/{id} |

**Ключевое:** при добавлении одного URL двумя пользователями — CanonicalResource один (дедупликация), UserBookmark у каждого свой.

## Критические пользовательские пути

### 🔴 Критические
1. **Регистрация и авторизация** — JWT, refresh tokens
2. **Добавление закладки** — URL → CanonicalResource → UserBookmark → очередь
3. **LLM-пайплайн** — extract → analyze → embed (Celery)
4. **Семантический поиск** — pgvector, embedding lookup

### 🟠 Важные
5. **Экспорт данных** — JSON / CSV / HTML
6. **Подписка и оплата** — T-Bank webhooks, квоты
7. **Telegram-бот** — добавление, команды
8. **Настройки** — язык, уведомления, квоты

### 🟡 Вспомогательные
9. **Коллекции и Reading Plans**
10. **VK-бот**
11. **Браузерное расширение**
12. **Автоочистка** (orphaned resources, старые записи)

## Технические риски

1. **Race condition в пайплайне** — если extract упал, LLM-задача не встаёт в очередь
2. **embedding_vector** — без `defer_embedding_vector()` 256-мерный вектор тянется при каждом запросе
3. **Дедупликация URL** — canonicalize_url должен давать одинаковый результат для разных форм одного URL
4. **Квоты** — при превышении должен возвращаться 429, не 500
